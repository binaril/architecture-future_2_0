# Обоснование Terraform-конфигурации «Будущее 2.0»

## 1. Состав инфраструктуры и выбор ресурсов

Конфигурация использует провайдер `kreuzwerker/docker` и разворачивает локальную среду из четырёх типов ресурсов.

### Docker Network (`docker_network.main`)

```
name   = "future20-${var.environment}-network"
driver = "bridge"
```

Изолированная bridge-сеть объединяет контейнеры `analytics_db` и `portal` в одном виртуальном сегменте. Контейнеры обращаются друг к другу по имени сервиса, не выходя на хост-интерфейс, — это ограничивает поверхность атаки. Имя сети включает `${var.environment}`, что позволяет одновременно держать несколько окружений (`dev`, `staging`) на одном Docker-хосте без конфликтов.

### Docker Volume (`docker_volume.db_data`)

```
name = "future20-${var.environment}-db-data"
```

Именованный volume монтируется в `/var/lib/postgresql/data` контейнера `analytics_db`. Данные переживают пересоздание контейнера (`terraform apply` после изменения образа). Без volume каждый `terraform destroy && apply` стирал бы всю аналитическую БД.

### Analytics DB — PostgreSQL 16 (`docker_container.analytics_db`)

**Выбор:** `postgres:16-alpine`, порт `var.db_port` (по умолчанию 5432, в `terraform.tfvars` — 5434).

| Параметр                                        | Значение                                       | Причина                                                                                     |
|-------------------------------------------------|------------------------------------------------|---------------------------------------------------------------------------------------------|
| `restart = "unless-stopped"`                    | контейнер поднимается после перезагрузки хоста | ETL-пайплайны ожидают доступность БД без ручного вмешательства                              |
| `env POSTGRES_DB/USER/PASSWORD`                 | из переменных Terraform                        | чувствительные данные не хардкодятся в `main.tf`; `db_password` помечена `sensitive = true` |
| volume mount `/var/lib/postgresql/data`         | именованный volume                             | персистентность данных между пересозданиями контейнера                                      |
| labels `service=analytics-db, project=future20` | Docker labels                                  | удобная фильтрация в `docker ps --filter label=project=future20`                            |

PostgreSQL заменяет managed ClickHouse для локального demo-окружения: он доступен без облачных учётных данных и запускается за секунды.

### Self-Service Portal — Nginx (`docker_container.portal`)

**Выбор:** `nginx:alpine`, порт `var.portal_port` (по умолчанию 8088).

| Параметр                                  | Значение                                     | Причина                                                                      |
|-------------------------------------------|----------------------------------------------|------------------------------------------------------------------------------|
| `restart = "unless-stopped"`              | автоперезапуск                               | доступность портала для пользователей без мониторинга                        |
| `depends_on = [analytics_db]`             | порядок старта                               | portal не поднимается раньше БД, устраняет race condition при первом `apply` |
| порт 8088 на хосте                        | совпадает с дефолтным портом Apache Superset | при замене Nginx на реальный Superset URL не меняется                        |
| labels `service=portal, project=future20` | Docker labels                                | единообразная маркировка ресурсов проекта                                    |

Nginx выступает заглушкой Superset в demo: проверяет сетевую связность и проброс порта без зависимости от облака.

## 2. Компоненты, управляемые вручную (post-deploy)

| Компонент                              | Причина ручного управления                                                                                    |
|----------------------------------------|---------------------------------------------------------------------------------------------------------------|
| Инициализация схемы БД                 | DDL-миграции (таблицы, индексы) не описаны в Terraform — это зона ответственности Liquibase/Flyway            |
| Конфигурация Nginx/Superset            | `nginx.conf` и дашборды Superset специфичны для окружения и данных, которые появятся после первичной загрузки |
| Первичная загрузка исторических данных | Одноразовая операция из legacy-источника (SQL Server 2008); инициируется скриптом вне Terraform               |
| Docker daemon на хосте                 | Провайдер `kreuzwerker/docker` требует работающего Docker Engine; его установка и настройка — вне Terraform   |

## 3. Декларативный подход — почему Terraform

### Воспроизводимость

Terraform-конфигурация описывает **желаемое состояние** набора Docker-ресурсов, а не последовательность `docker run` команд. `terraform apply` идемпотентен: повторный запуск не создаёт дублирующих контейнеров и не пересоздаёт неизменившиеся ресурсы.

### Версионирование и аудит

Все `.tf`-файлы хранятся в Git. Изменение порта или образа контейнера проходит через pull request с `terraform plan` в CI — аналог code review для инфраструктуры. История изменений Docker-окружения читается через `git log`, а не через `docker inspect`.

### Управление зависимостями

`depends_on = [docker_container.analytics_db]` в `docker_container.portal` гарантирует порядок создания ресурсов. При ручном управлении через `docker run` эта зависимость легко теряется при рефакторинге скриптов.

### Предотвращение drift

`terraform plan` обнаруживает ручные изменения контейнеров (изменение порта, удаление volume) и сигнализирует о расхождении между конфигурацией и фактическим состоянием.

## 4. Параметры для перехода dev → staging → production

| Параметр      | dev (`terraform.tfvars`)         | staging                          | production                      |
|---------------|----------------------------------|----------------------------------|---------------------------------|
| `environment` | `"dev"`                          | `"staging"`                      | `"prod"`                        |
| `db_port`     | 5434                             | 5432                             | managed PG (облако)             |
| `portal_port` | 8088                             | 8088                             | ALB / 443                       |
| Analytics DB  | `postgres:16-alpine` (контейнер) | `postgres:16-alpine` (контейнер) | `yandex_mdb_clickhouse_cluster` |
| Portal        | `nginx:alpine` (заглушка)        | Apache Superset (контейнер)      | Superset за ALB + SSL           |
| `docker_host` | `npipe:////./pipe/docker_engine` | Unix socket                      | не применимо (облако)           |

Все изменения окружения вносятся только в `terraform.tfvars` — код `main.tf` не меняется. Это демонстрирует принцип разделения конфигурации и инфраструктурного кода.

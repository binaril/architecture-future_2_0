# Задание 1. Целевая архитектура и приоритизация проблем «Будущее 2.0»

## 1. Целевая архитектура

Диаграмма контейнеров C4: [architecture.puml](./architecture.puml)

### Ключевые архитектурные решения

| Было                               | Стало                                                 | Зачем                                                        |
|------------------------------------|-------------------------------------------------------|--------------------------------------------------------------|
| SQL Server 2008 (монолитный DWH)   | ClickHouse / Redshift (аналитический DWH) + Data Lake | Масштабируемость, скорость запросов, поддержка vendor'ом     |
| PowerBuilder (desktop-клиент)      | МИС на React/Java (web)                               | Независимость от устаревшего стека, мобильный доступ         |
| Apache Camel ESB (монолитная шина) | Apache Kafka (event-driven)                           | Слабая связность доменов, масштабирование под новые партнёры |
| Вся бизнес-логика в DWH            | Бизнес-логика в доменах (Финтех, ИИ, Клиники)         | Независимые релизные циклы, time-to-market                   |
| Отчётность часами                  | Портал самообслуживания + ClickHouse                  | Отчёты за минуты, self-service без IT                        |

### Как архитектура поддерживает бизнес-сценарии

**Быстрая подготовка отчётности**
Данные из всех доменов стримятся в Data Lake через Kafka, трансформируются Airflow и загружаются в колоночный DWH (ClickHouse). Портал самообслуживания позволяет аналитику строить отчёты в рамках своих прав без участия IT. Время формирования сложных отчётов: с нескольких часов до 5–30 минут.

**Независимое развитие финтех- и ИИ-направлений**
Каждый домен (Финтех, ИИ, Клиники) имеет собственную БД и публикует события через Kafka — без прямых зависимостей от DWH. Финтех может выпускать продукты (кредит на лечение) без пересборки центрального хранилища.

**Масштабирование для новых бизнесов**
Подключение фармацевтических компаний и производителя оборудования сводится к интеграции через API Gateway / Kafka без изменения существующих доменов.

**Защита медицинских данных**
Медкарты, истории болезней и результаты исследований хранятся в изолированной МИС-БД. В аналитический DWH и портал попадают только агрегированные/обезличенные показатели — анонимизация выполняется на уровне ETL в Airflow.

## 2. Проблемные места текущей архитектуры

| # | Проблема                                 | Техническая причина                                                     | Затронутые бизнес-сценарии                            | Последствия                                                                          |
|---|------------------------------------------|-------------------------------------------------------------------------|-------------------------------------------------------|--------------------------------------------------------------------------------------|
| 1 | Монолитный DWH на SQL Server 2008        | EOL-система, вся логика и данные в одном месте                          | Все: отчётность, операции, интеграции                 | Единая точка отказа; безопасность не обеспечена; vendor не выпускает патчи           |
| 2 | Отчёты формируются часами                | Колоночные запросы на строковой OLTP-базе; конкуренция с OLAP-нагрузкой | Управленческая отчётность, финансовый анализ          | Запоздалые управленческие решения; снижение выручки из-за пропущенного окна          |
| 3 | Сильная связность доменов                | Бизнес-логика финтеха и ИИ вшита в DWH                                  | Независимые релизы финтех и ИИ-продуктов              | Изменение одного домена ломает соседние; time-to-market — месяцы                     |
| 4 | Медицинские данные в общем DWH           | Исторически единое хранилище без разделения                             | Соответствие 152-ФЗ, GDPR, внутренняя безопасность    | Юридические риски; невозможность использовать данные без анонимизации                |
| 5 | PowerBuilder как UI клиник               | Нет web/мобильного доступа; нет поддержки вендора                       | Работа операторов и врачей                            | Ошибки ввода; невозможность удалённой работы; кадровый дефицит PB-разработчиков      |
| 6 | Apache Camel ESB — монолитная интеграция | Не event-driven; нет буферизации и масштабирования                      | Подключение фармкомпаний и производителя оборудования | Шина не выдерживает нагрузку при добавлении партнёров; каскадные сбои                |
| 7 | Отсутствие каталога данных               | Нет метаданных, lineage и назначенных владельцев                        | Self-service аналитика                                | Аналитики тратят до 80% времени на поиск и проверку данных; низкое доверие к отчётам |
| 8 | Смешение OLTP и OLAP нагрузок            | Операционный и аналитический трафик на одной БД                         | Работа операторов клиник в часы запуска отчётов       | Замедление клинических операций; жалобы персонала; риск ошибок при вводе             |

## 3. Приоритизация проблем

### Матрица MoSCoW + Эйзенхауэр

| # | Проблема                          | MoSCoW     | Эйзенхауэр          | Обоснование (связь с бизнес-целями)                                                                              | Срок         |
|---|-----------------------------------|------------|---------------------|------------------------------------------------------------------------------------------------------------------|--------------|
| 1 | Монолитный DWH на SQL Server 2008 | **Must**   | Срочно + Важно      | Уязвимости безопасности без патчей; единая точка отказа для всего бизнеса; блокирует миграцию в облако           | 3–6 мес      |
| 4 | Медицинские данные в общем DWH    | **Must**   | Срочно + Важно      | Регуляторный риск (152-ФЗ, GDPR) — штрафы до 6% выручки; блокирует развитие ИИ-сервисов и витрины                | 3–6 мес      |
| 2 | Отчёты формируются часами         | **Must**   | Срочно + Важно      | Прямой бизнес-ущерб: решения принимаются с задержкой; без быстрой аналитики портал самообслуживания бессмысленен | 6–9 мес      |
| 3 | Сильная связность доменов         | **Should** | Не срочно + Важно   | Стратегически необходимо для независимого развития финтех и ИИ; замедляет time-to-market новых продуктов         | 6–12 мес     |
| 7 | Отсутствие каталога данных        | **Should** | Не срочно + Важно   | Без каталога self-service витрина не пользуется доверием; доля ручного труда аналитиков остаётся высокой         | 6–12 мес     |
| 6 | Apache Camel ESB                  | **Should** | Не срочно + Важно   | Текущей нагрузке хватает; критично при подключении фарм. партнёров — откладывается на фазу масштабирования       | 9–15 мес     |
| 8 | Смешение OLTP/OLAP нагрузок       | **Could**  | Срочно + Не важно   | Решается автоматически при разделении DWH и операционной системы; отдельных ресурсов не требует                  | В рамках п.1 |
| 5 | PowerBuilder UI                   | **Could**  | Срочно + Не важно   | Операционный дискомфорт, не угроза выживанию; заменяется после стабилизации новой МИС                            | 12–18 мес    |

### Итоговые выводы

**Первый приоритет (0–6 месяцев):** Миграция с SQL Server 2008 и изоляция медицинских данных. Это блокирующие риски: юридический, безопасности и непрерывности бизнеса. Без этого шага невозможно начать строить витрину данных.

**Второй приоритет (6–12 месяцев):** Запуск аналитического DWH + ETL + портала самообслуживания. Решает ключевую бизнес-задачу — быструю отчётность. Параллельно — каталог данных и декомпозиция доменной логики.

**Третий приоритет (12–18 месяцев):** Замена ESB на Kafka, постепенная замена PowerBuilder, подключение фарм. партнёров и производителя оборудования к новой event-driven шине.
